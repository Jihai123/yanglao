# 全国养老地区参数字典

> 状态：采集层 v2 + 运行时接入层（2026-09-04）。严格官方数据与“公开资料参考值”分层管理。

这个目录用于集中维护各省级地区的企业职工基本养老保险、灵活就业缴费基数和养老金计算参考参数。目标不是“只有最新年度才允许算”，而是尽量为 31 个省级地区保留最近可核验的官方参数；如果当前年度尚未公布或尚未核验，可以使用上一年度官方值作为规划保底，但必须明确显示年份和数据状态。

## 文件

- `employee-pension.v2.csv`：严格官方采集主表。把“缴费参数”和“养老金计算参考值”的来源等级、运行时接入资格拆开，避免一个字段来源较弱拖累同一地区另一个已经可靠的字段，也避免反向连带升级。
- `public-reference-overrides.v1.csv`：公开资料参考值层。只放“数值高度一致，但暂未找到可直接引用官方原文”的少量地区；必须显著标注非官方核验状态并允许用户修改，不计入严格官方覆盖率。
- `employee-pension.v1.csv`：第一版采集快照，保留用于审计演进，不再作为当前主表。
- `subregions.v1.csv`：省内分档数据。辽宁、吉林、湖北、广东、山东等不能用“一省一个数”简化。

## 缴费参数状态

- `current`：当前适用或本年度已正式公布的官方数值参数。
- `current_derived`：当前年度官方文件明确给出计算基准，同时官方规则明确上下限计算比例；数值由确定性公式得到。允许作为规划候选，但 UI 必须明确写“按官方基准与规则计算”，不能冒充“公告直接公布值”。
- `recent_fallback`：当前新值未核验时，最近一年度/最近适用期的可靠官方数值。允许作为规划保底候选，但 UI 必须写明年份和“最近可核验官方值”。
- `recent_fallback_derived`：最近年度官方文件给出基准且官方规则给出确定性比例，但没有单独找到最终上下限表。可作为保底规划候选，必须标明“按官方基准与规则计算”和年份。
- `stale`：至少两年以上旧值，仅作参考，默认不自动带入。
- `missing`：尚无可靠值。

## 养老金计算参考值状态

前台不应要求普通用户理解“养老金计发基数”这个专业词。运行时默认展示应类似：

> 养老金计算参考值：8,917 元/月  
> 2025年最近可核验官方值 · 可修改

严格官方主表中的状态：

- `current`：当前正式公布、可直接用于待遇计算的官方计发数值。
- `recent_fallback`：当前年度正式值尚未核验，使用最近年度正式官方计发值保底；必须显示年份。
- `current_provisional`：官方经办/人社渠道明确正在使用的“预发/暂用”计发值。可用于规划默认，但必须显著标注“预发参考值，正式基数公布后可能调整”。
- `recent_fallback_formula_anchor`：官方文件没有另起一个“计发基数”数值公告，但官方计发办法明确使用某个工资/基准指标，且该指标已有官方数值。它可以作为规划锚点自动带入，但 UI 必须写“按官方计发规则使用的参考值”，不能伪装成单独发布的计发基数。
- `recent_fallback_derived`：官方发布的是年度数值或其他可确定转换口径，月度规划值由无歧义的数学换算得到。必须保留原始值和换算来源，并标注“按官方数据折算”。
- `stale`：至少两年以上旧值，仅作参考，默认不自动带入。
- `missing`：没有达到严格官方自动带入门槛的可靠值。

独立公开资料参考层使用：

- `public_reference`：数值有较强公开资料/案例/公开文件佐证，但暂未找到可直接引用的省级官方正文。它不属于“官方已核验”。前台必须显示：`公开资料参考值 · 官方原文暂未找到，可自行修改`。

`current_provisional`、`*_formula_anchor`、`*_derived`、`public_reference` 都是为了让网站在“不编造数据”的前提下提高规划可用性，但证据等级必须在 UI 中明显区分。

## 来源与接入资格

严格官方 v2 主表使用：

- `contribution_source_level` + `contribution_runtime_eligible`
- `calc_base_source_level` + `calc_base_runtime_eligible`

原因很直接：例如陕西的 2025 缴费上下限已有税务官方原文，但 7881 养老金计算参考值仍没有陕西人社公开原文。正确做法是让严格官方层继续保持 `calc_base_runtime_eligible=false`，同时在独立 `public-reference-overrides.v1.csv` 中以公开资料参考值身份提供规划默认，而不是把整省一起“升级成官方”。

来源优先级：省级人社/税务/政府官方原文 > 官方政务转载 > 市县人社/政府完整转载省级文件 > 权威媒体明确报道官方文件 > 公开文件二次佐证 > 普通转载。

公开资料参考值不改变上述优先级，只是增加一个用户可见、可修改的规划兜底层。

## 强制规则

1. 有数值必须绑定年份、来源和核验状态；不能只有一个裸 `value`。
2. 上一年度官方值可以保底，但不能伪装成当前年度值。
3. 不允许把历史值自动加 3% 等增长率后冒充新年度政策参数。
4. 只有当“官方基准值 + 官方明确计算比例/公式”同时存在且不存在口径歧义时，才允许生成 `*_derived` 值；必须保存原始基准、公式来源，并在 UI 中标注为公式计算值。
5. 如果只有平均工资、但没有明确适用于养老待遇计发或该险种上下限的规则，不允许自行推导。
6. 缴费参数和养老金计算参考值必须分别评级、分别决定是否可接入；不得因为其中一个可靠就连带升级另一个。
7. `current_provisional` 必须来自官方人社/经办渠道，并在备注中明确“预发/暂用/正式值待调整”的性质。
8. `*_formula_anchor` 必须能从官方计发办法和官方数据直接建立用途关系；不能因为“数值看起来接近”就当计发基数。
9. `public_reference` 只能存在于独立公开资料参考层；严格官方主表仍保持原证据等级。每条必须有年份、来源 URL、`user_editable=true`、缺少官方原文的明确说明。
10. 省内有分档时必须保存子地区，运行时接入也必须让用户选对地区。只在官方明确存在地区差异时增加二级地区，不做全国 300 多地市穷举。
11. 新年度值上线后保留历史值；后续 schema 会升级为多期历史记录，不覆盖旧数据。
12. 没有稳定数值的地区宁可手填；不得用邻省、缴费基数或自行增长率代替。
13. 本目录仅存公共政策参数，不存任何用户出生年月、工资、缴费基数、账户余额、历史缴费或养老金测算结果。

## 数据上线标准

“采集到数字”不等于“可以上线自动带入”。生产接入至少满足：

1. 31/31 省级地区均有缴费规划参数或明确的省内分档；
2. 所有自动带入值都有年份、来源等级、来源 URL、状态；
3. 正式值、最近年度保底值、预发值、公式锚点、公式折算值、公开资料参考值能够被程序和 UI 区分；
4. 公开资料参考值不得标成“官方已核验”，且用户可自行覆盖；
5. 有官方明确例外地区的省份必须先选择正确子地区；未知子地区不得套用省级默认；
6. 剩余没有稳定默认值的地区必须可手工修改或只看资格；
7. 字典审计、运行时防漂移审计、Node 测试和浏览器回归全部通过后，才进入生产部署。

## 当前采集重点

第一阶段覆盖：

1. 企业职工养老保险缴费基数下限/上限；
2. 灵活就业缴费基数规则；
3. 基本养老金计算参考值/官方计发公式锚点；
4. 官方明确存在的省内分档；
5. 官方来源、年份、适用期和来源等级；
6. 少量明确标注的公开资料参考兜底。

城乡居民养老的地方基础养老金、缴费档次、政府补贴、长缴/高龄加发将在第二阶段单独建表，避免和职工养老参数混在一起。
