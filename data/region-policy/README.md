# 全国养老地区参数字典

> 状态：采集层 v2（2026-09-03）。**当前不参与生产运行时计算。**

这个目录用于集中维护各省级地区的企业职工基本养老保险、灵活就业缴费基数和养老金计发参数。目标不是“只有最新年度才允许算”，而是尽量为 31 个省级地区保留最近可核验的官方参数；如果当前年度尚未公布或尚未核验，可以使用上一年度官方值作为规划保底，但必须明确显示年份和数据状态。

## 文件

- `employee-pension.v2.csv`：当前采集主表。把“缴费参数”和“养老金计发基数”的来源等级、运行时接入资格拆开，避免一个字段来源较弱拖累同一地区另一个已经可靠的字段，也避免反向连带升级。
- `employee-pension.v1.csv`：第一版采集快照，保留用于审计演进，不再作为当前主表。
- `subregions.v1.csv`：省内分档数据。辽宁、吉林、湖北、广东等不能用“一省一个数”简化。

## 数据状态

- `current`：当前适用或本年度已正式公布的官方数值参数。
- `current_derived`：当前年度官方文件明确给出计算基准，同时官方规则明确上下限计算比例；数值由确定性公式得到。允许作为规划候选，但 UI 必须明确写“按官方基准与规则计算”，不能冒充“公告直接公布值”。
- `recent_fallback`：当前新值未核验时，最近一年度/最近适用期的可靠官方数值。允许作为规划保底候选，但 UI 必须写明年份和“最近可核验官方值”。
- `recent_fallback_derived`：最近年度官方文件给出基准且官方规则给出确定性比例，但没有单独找到最终上下限表。可作为保底规划候选，必须标明“按官方基准与规则计算”和年份。
- `stale`：至少两年以上旧值，仅作参考，默认不自动带入。
- `missing`：尚无可靠值。

## 来源与接入资格

v2 不再使用一个笼统的 `runtime_eligible`。改为：

- `contribution_source_level` + `contribution_runtime_eligible`
- `calc_base_source_level` + `calc_base_runtime_eligible`

原因很直接：例如陕西的2025缴费上下限已有税务官方原文，但7881养老金计发基数仍只有公开文件二次佐证。正确做法是允许未来单独接入前者，同时继续降低后者等级，而不是整省一起“通过”或一起“拒绝”。

来源优先级：省级人社/税务/政府官方原文 > 官方政务转载 > 市县人社/政府完整转载省级文件 > 权威媒体明确报道官方文件 > 公开文件二次佐证 > 普通转载。

两个 `*_runtime_eligible=true` 只表示对应参数组已达到“后续可考虑接入”的门槛，不代表当前网页已经使用它。生产接入前仍需单独评审、状态文案设计和浏览器回归。

## 强制规则

1. 有数值必须绑定年份、来源和核验状态；不能只有一个裸 `value`。
2. 上一年度官方值可以保底，但不能伪装成当前年度值。
3. 不允许把历史值自动加 3% 等增长率后冒充新年度政策参数。
4. 只有当“官方基准值 + 官方明确计算比例/公式”同时存在且不存在口径歧义时，才允许生成 `*_derived` 值；必须保存原始基准、公式来源，并在 UI 中标注为公式计算值。
5. 如果只有平均工资、但没有明确适用于该险种的上下限规则，不允许自行推导。
6. 缴费参数和养老金计发基数必须分别评级、分别决定是否可接入；不得因为其中一个可靠就连带升级另一个。
7. 省内有分档时必须保存子地区，运行时接入也必须让用户选对地区。
8. 新年度值上线后保留历史值；后续 schema 会升级为多期历史记录，不覆盖旧数据。
9. 非官方原文或二次佐证必须显式降级；没有足够证据时宁可留空。
10. 本目录仅存公共政策参数，不存任何用户出生年月、工资、缴费基数、账户余额、历史缴费或养老金测算结果。

## 当前采集重点

第一阶段只做：

1. 企业职工养老保险缴费基数下限/上限；
2. 灵活就业缴费基数规则；
3. 基本养老金计发基数；
4. 省内分档；
5. 官方来源、年份、适用期和来源等级。

城乡居民养老的地方基础养老金、缴费档次、政府补贴、长缴/高龄加发将在第二阶段单独建表，避免和职工养老参数混在一起。
